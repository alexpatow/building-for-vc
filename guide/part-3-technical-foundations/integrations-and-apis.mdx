Much of the technical work at a VC fund is building glue between tools. Connecting meeting notes to your CRM, data providers to your warehouse, portfolio data to dashboards. Some integrations exist out of the box, but many require custom code.

## Common Integration Patterns

**Tool-to-tool glue**: Connecting SaaS tools your team uses. Examples:

- Meeting transcription tool (Granola, Otter) → CRM (Attio) to automatically log conversations
- CRM → data warehouse for analysis
- Email → CRM to track outreach
- Calendar → CRM to log meetings

Some of these have out-of-box integrations. Many require custom code to map fields, handle authentication, and deal with differences in data models.

**Data vendor → your systems**: Pulling data from external providers and loading it into your infrastructure.

These integrations usually run on schedules (nightly data syncs) or in response to specific events (when you add a company to your CRM, enrich it with PitchBook data). See [Accessing Data](/guide/part-3-technical-foundations/data-providers/accessing-data) for how vendors deliver data.

**Internal service integrations**: If you're building multiple services (research platform, sourcing tool, internal APIs), they need to talk to each other. Your research platform might need portfolio company data from your data warehouse. Your sourcing tool might need to check your CRM to avoid suggesting companies you've already passed on.

**LLM/AI integrations**: Many funds are building features that use LLMs. These require integrations with OpenAI, Anthropic, or other providers. Often combined with your own data (RAG systems pulling from your research or CRM).

## Validating API Responses

The investment team usually sees a filled-in field or an empty one. On the engineering side there are at least three possibilities: the vendor had no estimate, the lookup failed, or the company genuinely reported zero. Preserve the difference. If a request fails, keep the last successful observation and its date. Turning a failed request into a zero can make a company look like it lost its entire team overnight.

The biggest source of problems in integrations is trusting external APIs to return what you expect. API schemas change. Vendors return errors in unexpected formats. Required fields are sometimes null. Data types don't match documentation.

For TypeScript: **[Zod](https://zod.dev/)**. For Python: **[Pydantic](https://docs.pydantic.dev/)**. These libraries let you define schemas for your data and automatically validate objects against them.

```typescript
// TypeScript with Zod
import { z } from "zod"

const CompanySchema = z.object({
  id: z.string(),
  name: z.string(),
  founded_date: z.string().datetime().nullish(),
  funding_total: z.number().nonnegative().nullish(),
  employee_count: z.number().int().nonnegative().nullish(),
})

// When you get data from an API
const response = await fetch("https://api.vendor.com/companies/123")
if (!response.ok) throw new Error(`Vendor returned HTTP ${response.status}`)
const data = await response.json()

// Validate it
const company = CompanySchema.parse(data) // Throws if the response is invalid
```

```python
# Python with Pydantic
import requests
from pydantic import BaseModel, Field
from datetime import datetime
from typing import Optional

class Company(BaseModel):
    id: str
    name: str
    founded_date: Optional[datetime] = None
    funding_total: Optional[float] = Field(default=None, ge=0)
    employee_count: Optional[int] = Field(default=None, ge=0)

# When you get data from an API
response = requests.get('https://api.vendor.com/companies/123', timeout=30)
response.raise_for_status()
company = Company.model_validate(response.json())  # Raises on invalid data
```

Suppose you’re importing 500 companies. Acme’s founding date is missing, which the schema allows. Its employee count comes back as “about fifty,” which it rejects. Catch the validation error for that row before writing to the company table. Save the rejected row with the vendor’s name, record ID, and the field that failed, then carry on with the other 499. The deal team still sees Acme’s last good headcount and its date. Once you’ve fixed the mapping or the vendor has corrected the record, you can retry Acme on its own.

**Validate both inbound and outbound data**

Take a vendor that accepts either a company ID or a domain for enrichment. If the CRM contains neither, send the record back for completion. Retrying the same empty request overnight buys another error. If the request was valid but the service timed out, that belongs in the retry queue. Both cases can look like ‘no company data’ to the deal team unless you record the outcome.

When you're calling external APIs, validate the data you're sending. This catches mistakes in your code before they hit the vendor's API. When you're exposing APIs for internal use, validate inputs from callers.

## Webhook Handling

Many vendors (especially CRM systems) provide webhooks: they call your HTTP endpoint when events happen (company updated, deal stage changed, meeting logged). This is more efficient than polling their API constantly.

Register an HTTPS endpoint with the vendor. For local testing with dummy data, [webhook.site](https://webhook.site/) lets you inspect an incoming request.

**Verify signatures**: Always verify that webhooks actually came from the vendor. They send a signature (usually HMAC of the body using a shared secret). Verify this before processing.

**Handle idempotency**: Vendors may send the same webhook multiple times (network retries, their infrastructure issues). Make your webhook handler idempotent: processing the same event twice should be safe. Track event IDs you've seen and skip duplicates.

**Return quickly**: Webhook handlers should return 200 OK within a few seconds. Don't do expensive processing in the handler itself. Accept the webhook, queue the work, and return success. Process asynchronously.

Consider the handoff between your endpoint and the worker that updates the CRM. If you acknowledge the webhook before saving anything and the process exits, the vendor thinks the update succeeded. If you save the job and the acknowledgement gets lost, the vendor may send it again. Store the event ID with the job and enforce uniqueness when you enqueue it. A second delivery should find the work already recorded. Have the worker use the same ID for any downstream write that supports idempotency.

For someone running the pipeline meeting, the difference is visible: the company moves stages once, and the notes stay attached even if the CRM took a minute to respond. Keep failed jobs inspectable so you can replay one company’s update without importing the whole pipeline again.

## Rate Limits and API Costs

Your vendor might give the whole fund one request budget. If the nightly market-map refresh uses it up, an investor opening a company before a meeting hits the same limit. Have the background jobs share a rate limiter and leave room for interactive lookups. Check whether the quota counts requests or companies returned. Batching a hundred companies into one call can save you ninety-nine requests while costing exactly the same number of credits.

If you have to stop a long import, save the next page cursor after the current page is stored. On restart, a repeated page should be cheap to process and a failed page should still be waiting for you. This also gives you something useful to tell the deal team when only part of their watchlist has been refreshed.

Other ways to keep API costs down:

- Only request data you actually need
- Cache responses so you don't request the same data repeatedly
- Batch requests when possible
- Validate input before making API calls (don't waste money on requests that will fail)

Monitor your API spending. Set up alerts when spending exceeds thresholds.

## Retry failures selectively

**Categorize errors**

- **Retriable**: 429 (rate limit), 503 (service unavailable), 504 (timeout), network errors. Retry with backoff.
- **Non-retriable**: 400 (bad request), 401 (unauthorized), 403 (forbidden), 404 (not found). Fix the problem or skip the request.
- **Context-dependent**: 500 (server error) might be temporary or might indicate a vendor bug. Retry a few times, but not indefinitely.

For transient failures, back off between attempts, add jitter, and cap retries. Log the record ID, HTTP status if available, and next retry time.

For example, space retries a second, two seconds, four seconds, then eight seconds apart and add some randomness so every worker doesn’t retry at once. Respect the vendor’s retry instructions. A timeout on a write deserves special care: the vendor may already have saved the record. Check its status or reuse its idempotency key before sending it again.

**Use transactions**

When working with databases, wrap operations that need to succeed together in transactions. If anything fails, the transaction rolls back.

```typescript
await db.transaction(async (tx) => {
  const [company] = await tx.insert(companies).values({ id: data.id, name: data.name }).returning()

  for (const round of data.funding_rounds) {
    await tx.insert(fundingRounds).values({
      company_id: company.id,
      round_name: round.name,
      amount: round.amount,
    })
  }
  // If any insert fails, everything rolls back
})
```

## Working with LLM Providers

**Use an AI gateway for failover**. LLM providers have frequent outages and rate limits. Services like [Vercel's AI SDK](https://ai-sdk.dev/) or [LiteLLM](https://www.litellm.ai/) provide automatic failover between providers.

**Handle streaming responses**. When building UIs, you'll want LLM APIs to stream tokens incrementally.

**Set timeouts**. LLM requests can take 30+ seconds. Set 60-90 second timeouts so slow requests don't block indefinitely.

When you configure failover, check which requests can go to the secondary provider. If a document-processing job can only send board packs to one approved endpoint, an outage should pause that job. A retry that silently changes the destination also changes where the board pack went.

## Authentication Patterns

An API token identifies the service making the request. For a scheduled sync, use a service identity with the access that one job needs. If it stops working when an associate leaves the fund, the job was probably running under the wrong account.

For internal dashboards, prefer OAuth (Google, Microsoft) over managing separate passwords.

Keep vendor tokens in your deployment’s secrets store. The [security chapter](/guide/part-3-technical-foundations/security-and-compliance) covers scoping and revoking access.
