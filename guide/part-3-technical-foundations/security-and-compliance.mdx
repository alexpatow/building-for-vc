Your fund's security model needs to work even when someone builds a new application in an afternoon. Investors, legal, and fund ops can increasingly build their own tools. Agents can search documents, query your CRM, and take actions across systems. That's useful, but it puts more responsibility on the infrastructure underneath them.

You can't review every prompt or rely on everyone building an application to understand security. Make identity, permissions, data access, deployment, and logging reusable. A new application should inherit the fund's boundaries instead of inventing its own.

## Know What You're Protecting

Start with the data and its permitted uses. "Internal" is too broad a classification to make useful access decisions.

**LP information** includes contact details, tax identifiers, bank details, commitments, and subscription documents. Collect only what your workflow needs. If the fund administrator holds identity documents, your dashboard probably doesn't need another copy.

**Company information** includes board materials, cap tables, financials, customer lists, and diligence documents. Confidential information can also be material non-public information (MNPI), but not every private company update automatically has that legal classification. Ask compliance how to handle it. Confidentiality obligations still matter regardless of the label.

**Investment research** includes memos, IC discussions, reference calls, and proprietary analysis. A memo may combine public research with restricted information. Don't make the whole document broadly accessible just because most of it is public.

**Personal information** exists outside LP records too. Founder profiles, reference notes, recruiting records, emails, and meeting transcripts can contain personal data. A useful relationship tool doesn't need to retain every personal detail someone mentions.

For each source, record who owns it, who can access it, what uses are allowed, where it can be sent, and how long it should be retained. Include vendor licensing restrictions: being able to query a dataset doesn't necessarily mean you can redistribute it or send it to another service.

## Build Access Controls Below the Application

Use an established identity provider and authentication libraries. Require MFA, preferably phishing-resistant methods where supported, and use SSO so access can be removed centrally. Authentication establishes who someone is. You still need to decide what they're allowed to do.

**Enforce authorization on the server**. Check access on every request, including downloads, exports, background jobs, and agent tool calls. A hidden button or a filtered frontend list isn't an access control. The [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) is a useful implementation reference.

**Combine roles with access to specific records and sources**. "Partner" or "associate" is a starting point, not a complete policy. Someone may have access to one company's board materials but not another's, or to company research but not LP records. Preserve source permissions when you ingest documents. A summary combining several sources must not expose restricted information to someone who couldn't read those sources.

**Keep the caller's identity through the whole request**. If a partner builds an app and shares it with an associate, the app must use the associate's permissions when they open it. Don't silently run every request with the creator's credentials. Scheduled jobs need an explicitly scoped service identity and an owner.

**Use database controls where they help**. Row-Level Security (RLS) can enforce per-company or per-user boundaries, but only if queries run with the intended identity and policy context. Database owners and privileged service accounts may bypass those policies. Test the actual application's connection and execution path, not just a query run as a restricted test user.

**Test denied access**. Check what happens when someone changes a company ID in a request, opens another LP's document URL, calls an API directly, or uses a session after access is revoked. Include search indexes, caches, exports, and generated summaries. A correct dashboard filter doesn't prove those paths are protected.

Remove access when people leave or change roles. Revoke sessions and integration tokens as well as disabling the main account. Review service accounts and shared links too; they don't disappear when someone leaves.

## Give People a Safe Way to Build

Provide a small set of reusable pieces:

- A deployment template with authentication, server-side access checks, and logging already configured
- Approved APIs or views that expose only the data a workflow needs
- Separate development and production environments, using synthetic or minimized data for experiments
- Centrally managed secrets and narrowly scoped integration permissions
- A way to disable an application or revoke its access without taking down everything else

A generated frontend shouldn't connect directly to your warehouse with a privileged credential. Put sensitive operations behind an API that checks identity and permissions. If your database platform supports direct client access, verify its policies and client credentials are safe for that use. Never ship a service-role key to the browser.

Keep an inventory of applications connected to fund systems: owner, users, data sources, permissions, deployment, and support expectations. Personal experiments become shared infrastructure surprisingly quickly. Agree when engineering review is needed, especially before granting sensitive access, enabling external sharing, or writing to authoritative records.

Review the resulting application, not just the instructions used to generate it. Check dependencies, public routes, storage access, secrets, and authorization. Run automated dependency and secret checks, then test the important boundaries yourself. A successful build and a reassuring AI review don't establish that an app is secure.

## AI Tools and Agents Change the Data Flow

An assistant connected to email, files, and your CRM is another application with access to fund data. A prompt doesn't make that access less consequential. Review what it can read, where it sends information, and what it can change.

### Review the Whole Service, Not Just the Model

Before connecting sensitive data, check the product and account configuration you're actually using:

- Can inputs, outputs, or uploaded files be used for training? Under what terms?
- What is retained in chats, API logs, file storage, traces, and backups? Can retention be configured?
- Who can install connectors, grant scopes, share results, or publish applications?
- Can you audit usage, revoke access, and export or delete stored data?

**Zero Data Retention (ZDR)** is worth asking for when you send confidential fund data to a model provider. It concerns retention of request content after processing, which is separate from whether the provider uses that content for training. Check the agreement and configuration for the exact product, model, and features you use: what content is covered, what metadata remains, and what exceptions apply. ZDR may require approval or disable features that store state. [Anthropic's scope documentation](https://privacy.claude.com/en/articles/8956058-i-have-a-zero-data-retention-agreement-with-anthropic-what-products-does-it-apply-to) illustrates why you need to check the specific service rather than assume an agreement covers every product.

Trace the rest of the request too. A model provider's ZDR agreement doesn't stop your application, gateway, tracing service, or connector from storing the same prompt and response. For a board-pack summarizer, check every place the uploaded PDF and extracted text pass through, including error logs.

**Subprocessors** are the other companies a vendor uses to process data on its behalf. Review the vendor's current subprocessor list alongside its data processing agreement (DPA). Check what each company does, which data it receives, processing locations, and the arrangements for international transfers. Hosting, support, and safety review can involve different providers; a chosen hosting region alone doesn't describe the whole chain. [Anthropic lists its subprocessors in its Trust Center](https://trust.anthropic.com/).

Subscribe to subprocessor change notices and assign someone to review them. Separately assess services you connect yourself, such as an MCP server or automation platform: they may have their own terms and subprocessors outside your model provider's agreement.

Use approved work accounts and document which data each service can receive. Send only the fields and documents required for the task. Review again when you enable a new connector or capability; approval for a coding assistant isn't automatically approval to connect the whole document store.

### Treat Retrieved Content as Untrusted Input

An agent reading an inbound email, pitch deck, website, or repository can encounter instructions planted in that content. This is indirect prompt injection. For example, a deck could tell an assistant to fetch an internal memo and send it to an external URL. The [OWASP prompt injection guidance](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) describes this class of attack.

A system prompt telling the agent to ignore malicious instructions isn't a security boundary. Reduce what a compromised or mistaken agent can do:

- Start with narrowly scoped, read-only tools. Read-only access still needs limits on which data can be read and where results can go.
- Enforce permissions in the tool backend using the caller's identity. Don't let the model choose which user's privileges to assume.
- Separate retrieval from actions that send information externally or change records. Validate tool arguments and allowed destinations outside the model.
- Require human approval for consequential actions, showing the exact recipient, records, and payload. Check permissions again when the action executes.
- Limit steps, runtime, spending, and retries. Make it possible to stop a run and revoke its credentials.

Keep audit records of the initiating user, tools called, records affected, approvals, and outcome. Log enough to investigate without indiscriminately storing sensitive prompts and responses.

### Connectors, MCP Servers, and Code Execution

Review connector scopes and the code you're installing. An MCP server, skill, plugin, or dependency may execute code or access data. A registry listing doesn't replace that review. For MCP integrations, follow the protocol's [security best practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices), including appropriate token validation and avoiding token passthrough.

Run agent-generated code in an isolated environment with limited filesystem access, scoped credentials, and network restrictions. A sandbox with unrestricted outbound access can still send out any data you put inside it. Keep production administrator credentials out of agent environments.

Don't assume bringing everything in-house solves this. A local model connected to an overprivileged tool can still expose data or make unauthorized changes.

## Keep the Operational Basics Working

**Protect accounts and devices**. Use managed devices, disk encryption, updates, and a process for lost laptops and compromised accounts. Protect email as carefully as the applications you build; password resets and sensitive documents often flow through it.

**Encrypt and manage secrets**. Use HTTPS and managed encryption at rest. Put server credentials in a secrets manager or protected deployment configuration. Prefer short-lived, scoped credentials where supported. Follow the [OWASP secrets management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html): plan issuance, rotation, revocation, and recovery. Replace credentials immediately when exposed.

**Patch what you run**. Track application dependencies, integration code, and deployed services. Assign someone to act on security alerts. Fewer custom components mean fewer things you need to patch.

**Back up and restore**. Keep backups protected from the same account or mistake that could destroy production. Test restoring them. Syncing data to another system isn't necessarily a backup; it may sync the deletion too.

**Monitor meaningful events**. Watch for unusual downloads, permission changes, new integrations, unexpected external destinations, and failed access checks. Decide who receives alerts and what they should do.

**Protect money movement**. Verify changes to bank details and payment instructions through an independently established channel. An authenticated email, plausible document, or agent-generated recommendation isn't sufficient approval to move money.

## Compliance: Establish What Applies to Your Fund

Don't turn a general guide into your fund's legal policy. Map obligations with compliance or counsel, then turn them into concrete requirements for access, processing, retention, and incident response.

**US adviser status isn't determined by a single AUM threshold**. The exemption for advisers solely to qualifying venture capital funds is distinct from the private fund adviser exemption for advisers with less than $150 million in private fund assets under management in the United States. Eligibility and other obligations depend on the facts. See the [SEC's exemption rules](https://www.sec.gov/rules-regulations/2011/06/exemptions-advisers-venture-capital-funds-private-fund-advisers-less-150-million-assets-under), and have counsel confirm your position.

**Check applicable incident-response requirements**. The amended US Regulation S-P requires covered institutions, including SEC-registered investment advisers, to maintain incident-response procedures and address service-provider oversight and notification obligations. The compliance dates were December 3, 2025 for larger entities and June 3, 2026 for smaller entities. Use the [SEC's compliance guide](https://www.sec.gov/files/rules/final/2024/regulation-s-p-small-entity-compliance-guide.pdf) to check scope with your compliance team. Don't assume every VC fund is covered, or that exemption from registration removes all privacy obligations.

**Consider privacy beyond securities regulation**. Where GDPR applies, work with counsel on lawful processing, data minimization, processor arrangements, international transfers, and individuals' rights. Adding AI doesn't remove those obligations. The [European Commission's guidance](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/obligations_en) is a starting point. Assess the specific use of AI too: a research assistant and a tool used to screen job applicants can raise different requirements.

**Define retention by record type**. Avoid a blanket "keep everything" or "delete after five years" rule. Compliance should specify required records, retention periods, legal holds, and deletion procedures. Cover source documents, extracted data, embeddings, generated reports, logs, and backups. Document how deletion reaches derived copies and how expired data is handled after a restore. This also qualifies the append-only approach in [Data Modeling](/guide/part-3-technical-foundations/data-modeling#temporal-data-and-history): preserving useful history doesn't justify keeping personal or restricted data indefinitely.

Document decisions in a form you can maintain: approved services, permitted data uses, access rules, owners, retention schedules, and review dates. Compliance review works better when you can show an actual data flow and the controls enforcing it.

## Prepare for an Incident Before You Have One

Have a short response plan with named contacts, an alternative communication channel, and access to the accounts needed to contain an incident. Include your IT provider, compliance lead, counsel, and relevant vendors. Know who can make decisions when the usual owner is unavailable.

Practice a realistic scenario: an app exposes LP documents, a partner's account is compromised, or an agent sends board material to an external destination. Can you disable the integration, revoke tokens, preserve evidence, identify affected data, and restore service?

Notification requirements vary. For example, where GDPR requires notification to a supervisory authority, the deadline is without undue delay and, where feasible, within 72 hours of awareness. Other rules and contracts can impose different obligations. Counsel should determine who must be notified and when. Escalate promptly so they have time to assess; don't wait for a complete forensic report.

After containment, fix the underlying failure and check other applications using the same template or credentials. One insecure generated app may reveal a gap in the shared foundation.

## Decide Where You Need Outside Help

Use managed services, but understand which responsibilities remain yours. A provider can secure its infrastructure while your application still exposes every LP's records through a missing authorization check.

A vendor's [SOC 2 report](https://www.aicpa-cima.com/resources/landing/system-and-organization-controls-soc-suite-of-services) can support due diligence. Read the scope, period, exceptions, and controls you're expected to operate. It doesn't prove that your configuration or application is secure. Whether your own fund needs an assurance report depends on its obligations and stakeholder needs.

Get independent security review or penetration testing where the exposure warrants it, especially for LP portals, sensitive integrations, and applications that can act across systems. Choose monitoring and data-loss controls based on the data and capabilities involved. A five-person fund can still have a tool with access to every board pack.
